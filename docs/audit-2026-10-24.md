# ForkPanel 深度审计（2026-10-24）

> 上一轮审计 [`audit-2026-10-17.md`](./audit-2026-10-17.md) 的 P0/P1/P2 全部闭环后的**第二轮**。
> 本轮不再重复上轮视角（能力矩阵、依赖预算、拆分大视图），改为按**缺陷类型**横切：
> 假控制 / 静默失败 / 恒绿守卫 / 不可观测 / 安全护栏 / 契约漂移。

## 审计方法

1. **按缺陷类型分片**，5 路并行扫描（后端 103 个 `.rs` + 前端 125 个 `.vue|.ts` 全量覆盖）。
2. **实证优先**：每条结论必须给出 `文件:行号` 与可复现的 grep 证据，禁止「看起来像」。
3. **子代理报告一律复核**：子代理会张冠李戴、也会把合理设计当 bug。本轮报告的
   每条 🔴 与绝大多数 🟡 已由人工 `sed`/`grep` 复核，标注如下：
   - **✅ 实证**：已读源码确认行号存在且描述属实；
   - **⚠️ 待复核**：仅子代理报告，尚未逐条读码确认（**不得据此直接开工**）。
4. **反向证伪**：写「没有 X」前先 grep；写「已有 X」前先 `git status`（WIP 会冒充已提交）。

### 本轮刻意排除的项（避免重复排查）

## 一、🔴 P0：必须修（安全 / 数据后果 / 用户被误导）

### P0-1 `mkdir` 绕过敏感兜底 ✅实证

`crates/panel-api/src/routes/files.rs:318-331`

`resolve_new` 之后**直接** `create_dir`，**没有** `ensure_not_sensitive`。
对比同文件：`write:290`、`remove:337`、`rename:592`、`trash_restore:517` **全都调了**。

- 后果：持 `file.write` 者可在 `/etc/cron.d/`、`/etc/sudoers.d/`、`/etc/profile.d/`、
  `/etc/systemd/system/` 等黑名单前缀下**建目录**，为后续落文件铺路。
- 这正是 `/etc/passwd` 事故（2026-10-21）的同族模式：**只挡住了一部分写入口**。

### P0-2 `chmod` 同样漏查敏感 ✅实证

`crates/panel-api/src/routes/files.rs:626-631`：`resolve` 后直接 `parse_mode`，无敏感校验。

- 后果：可把 `/etc/ssh/` 下的主机私钥、`/etc/ssl/private/` 下的证书改成 0644 扩大暴露面。
- 注：`parse_mode` 已用 `> 0o777` 挡住 setuid/setgid（:619），这块是对的。

### P0-3 敏感黑名单漏掉发行版 systemd 单元目录 ✅实证

`crates/panel-os/src/sensitive.rs:81` 只收了 `"/etc/systemd/"`、`"/run/systemd/"`。

- 漏：`/lib/systemd/`、`/usr/lib/systemd/` —— 这**正是发行版包单元的默认目录**
  （Debian 上 `/lib` 是 `/usr/lib` 的 symlink，`/etc/systemd/system` 多为管理员覆盖位）。
- 后果：往 `/usr/lib/systemd/system/evil.service` 写 `ExecStart=` = **以 root 执行任意代码**，
  完全命中模块头 :12 的收录标准。

### P0-4 敏感黑名单漏 `/etc/fstab` ✅实证

`crates/panel-os/src/sensitive.rs:31-65`（`DENY_EXACT`）无 `fstab`。

- 后果：写坏 ⇒ 下次重启挂载失败 ⇒ **不可启动**，与已收录的 `nftables.conf`（:52）同族
  （同样是「改坏=下次启动就进不去」）。

### P0-5 敏感黑名单漏面板库本体 `panel.db` ✅实证

`crates/panel-os/src/paths.rs:31`：`sqlite_path = data_dir().join("panel.db")`。
黑名单只精确收了同目录的 `master.key`（`sensitive.rs:49`）。

- 后果：覆盖该文件 = 会话、审计、凭据、LLM 配置全毁，**面板即登录系统立刻不可登录**。
- ⚠ 修法注意：数据目录可由 `[paths].data` 配置，黑名单是**字符串**匹配 ⇒ 需按运行时
  实际路径动态判定，不能只加一条硬编码常量。

### P0-6 `db_connections.tls_mode` 是假控制（且静默吞掉用户意图）✅实证

- 契约声明：`docs/api/openapi.yaml:870`（响应）、`:905`（`DbConnectionCreate` 请求，
  enum `disable|prefer|require`，default `prefer`）；DB 列：`migrations/001_init.sql:109`。
- **Rust 侧零引用**：`grep -rn "tls_mode" crates/` 无任何命中（整个 `databases.rs` 连
  `tls` 字样都没有，见 `CONN_SELECT`/`INSERT` :68/:188）。
- 更糟：`PanelJson`（`crates/panel-api/src/extract.rs:30`）**没有** `deny_unknown_fields`
  （该属性目前只在 `panel-cli/src/config.rs` 的 TOML 配置上）⇒ 用户按契约提交
  `tls_mode: "require"` 被**静默丢弃、返回成功**，实际连库不强制 TLS。
- 后果：以为「强制 TLS」，实际 MySQL/PG **凭据与数据明文传输**。这是「假控制」里最危险的
  形态——**伪装成已做**，且静默降级。

### P0-7 MFA 恢复码消费后写库失败被吞 ⇒ 可无限复用 ✅实证

`crates/panel-api/src/routes/auth.rs:162`：`let _ = state.db.exec(...)` 丢弃 UPDATE 结果。

- 链路：:158 命中并 `codes.remove(pos)` → :159 序列化剩余 → :162 写库结果丢弃 → 登录照常放行。
- 后果：写库失败时该恢复码仍留在库里，**可无限次复用**且无任何留痕（MFA 的第二因子被架空）。

### P0-8 计划任务被超时强杀仍记为「成功」✅实证

`crates/panel-api/src/routes/cron.rs:531`：`let code = out.code.unwrap_or(0);`

- `cmd::run` 超时/被信号杀死时返回 `code: None`（`cmd.rs:222-227`），此处降级为 0。
- 后果：`TaskState::Ok` + `status_text="ok"` + `exit 0` —— 用户以为脚本跑成功了。
- 同源：`:550` `let _ = self.db.exec(...)` 写 `last_run_at/last_status` 也被吞
  ⇒ 本轮失败没写进去，列表页继续显示上一次的 ok。

### P0-9 sshd 配置回滚失败却谎称「已自动回滚」✅实证

`crates/panel-os/src/linux/security.rs:301`：`let _ = std::fs::copy(&backup, &path); // 回滚`

- 后果：回滚失败无日志、无返回值，而错误文案宣称「已自动回滚（原配置已恢复）」。
  用户据此重启 sshd ⇒ **可能被锁在门外**，且完全无感知。

### P0-10 前端把「请求失败」渲染成「无风险」✅实证

`forkpanel-frontend/src/views/SecurityView.vue:54`（:56 同）：

```ts
const b = await api.get<BaselineItem[]>(API.security.baseline()).catch(() => null)
baseline.value = Array.isArray(b) ? b : []
```

- 后果：基线接口一挂，汇总卡按空数组算出 `risks=0`，直接显示「无风险项」——
  **把故障渲染成合规**，是安全页最不能犯的错。

### P0-11 契约漂移：`POST /containers/compose/{project}/act` 未进契约 ✅实证

- 后端已装配：`routes.rs:324`；前端已调用：`endpoints.ts:257-258`。
- `openapi.yaml` 的容器段（:3010-3270）只有 `/containers/compose`（:3163）与
  `/containers/stacks/{project}`（:3181），**没有** `compose/{project}/act`。
- ⚠ 结构性教训：`check-api-contract.sh` 的 md5 比对只能发现「两份不一致」，
  对「**两份一起漏了同一个端点**」完全无感 —— 契约完整度号称 100%，此处是实证缺口。

### B. 资源无界与不可观测（5 条）

- **P1-9 ✅ 会话永不回收**：`auth.rs:354` 定义 `SessionCache::sweep()`，但**全仓无调用点**
  （`grep -rn "\.sweep(\|session.*sweep" crates/` 为空），`builtin_schedules` 也未注册——
  注释却写「合并进统一调度器」。只有「过期后再访问一次」或显式登出才回收 ⇒
  关掉浏览器的用户会话在内存 map 与 `sessions` 表里**单调增长**。
- **P1-10 ✅ 内部周期任务无超时**：`panel-task/src/scheduler.rs:163` 直接 `f().await`，
  无 `tokio::time::timeout`（对比 `lib.rs:381` 的 `body.run()` 有超时），且只有返回 `Err`
  才 `tracing::warn!` ⇒ 任一 job **挂住**（不返回、不报错）则该 schedule 永久停摆，
  定时备份/清理从此不再执行，界面与 stderr 都看不出异常。
- **P1-11 ✅ 每日库备份占死 worker**：`panel-cli/src/main.rs:925` 直接同步调
  `panel_db::backup_file`（`wal_checkpoint` + `VACUUM INTO`），无 `spawn_blocking`；
  runtime 只有 2~3 个 worker ⇒ 备份期间 HTTP 与 SSE 心跳一起卡（**注意**：上轮 P1-1 只包了
  手动备份那条，这是**另一处**遗漏）。
- **P1-12 ✅ 只写不读的无界 map + 语义错**：`panel-task/src/progress.rs:46` `latest` 每个
  任务 id 插一条、永不回收；而 `subscribe()`(:52) **从不读它**——注释说的「新订阅者立即
  拿到当前值」并未实现；`listener_count()`(:56) 却把 `latest.len()` 当**订阅者数量**返回
  （语义完全错位，幸而全项目无调用者）。
- **P1-13 ⚠️ 任务日志写 `/tmp` 根目录无裁剪**：`services/packages.rs:513`（同源
  `backups.rs:957`）直接写 `/tmp/panel-task-<id>.log`；对比 `cron.rs:519-525` 用
  `panel-cron-logs/` 子目录 + `TASK_LOG_KEEP=50` ⇒ 长期运行把 /tmp 慢慢塞满，
  且 /tmp 被系统清理后任务页「查看输出」集体 404。

### C. 静默失败（6 条）

- **P1-14 ⚠️ 任务终态写库失败被吞**：`panel-task/src/lib.rs:374`/`:396`

- **P1-19 ⚠️ 高成本写端点大面积漏限流**：`ratelimit.rs:197-219` 的守卫只登记 6 个

## 五、本轮方法论（可复用）

1. **按缺陷类型而非模块分片**：同一类 bug 会跨模块复现（「假控制」在配置/DB 列/能力位/
   契约字段上各有一例），按模块扫描会漏掉同族。
2. **假控制的判据是「有没有第二处读取点」**：`grep` 字段名，若命中只在
   「定义 + 序列化 + 示例 + 测试 + 注释」里出现，就是假控制。**反向也要查**
   （代码读了但没有任何来源能配 ⇒ 永远走默认值）。
3. **静默失败分两类，都要查**：①吞错（`let _ =` / `.ok()` / 空 catch）；
   ②**谎报**（失败路径却向用户输出「已回滚」「成功」「无风险」）——②比①更危险，
   因为它主动制造错误认知。
4. **恒绿守卫的通用骗法**：先问「什么改动能骗过它」。高频答案：判据指向错（注释/同源）、
   环境不具备时走「跳过」而非 `[skip]`、失败被 `2>/dev/null` 吞掉、不校验**提取条数**。
5. **契约 md5 门禁的结构性盲区**：只能发现「两份不一致」，发现不了「两份一起漏」。
   要补一条「后端路由集合 ⊆ 契约 paths」的**单向包含**断言。
6. **子代理报告必须复核**：本轮 5 路报告约 55 条，人工复核后保留约 45 条，
   剔除/降级若干（如 SSE `Lagged` 因前端 EventSource 自动重连而从 🟡 降为 🟢）。
