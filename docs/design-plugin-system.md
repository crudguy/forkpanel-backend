# ForkPanel 插件系统 · 架构方案（T5）

> 状态：**设计稿（未实施）**。本文档只定边界与协议，落地前需按分期逐张卡片评审。
>
> 前置设施（均已就位）：能力矩阵、任务中心、RBAC（含自定义角色）、审计日志、站内通知、
> `cmd.rs` 子进程唯一出口、分层门禁 CI。
>
> 姊妹文档：`design-multi-node.md`（#53）。两者同一个命题：**在单机基线上做扩展，但不得让
> 扩展代码获得比面板自身更高的信任**。

## 1. 背景与目标

插件系统的诉求是「让面板能被扩展，而不必改面板代码」——典型场景是通知渠道（企业微信/钉钉/飞书）、
自定义监控采集（GPU、UPS、业务指标）、自定义安全基线检查项。

**目标**
1. 管理员能把一个插件放进面板、看到它**声明要什么权限**、显式批准后启用
2. 插件能：读面板允许它读的观测数据、向面板投递通知、产出结构化观测项
3. 插件的崩溃、超时、输出异常**不得影响面板本体**

**非目标（定位使然，明确不做）**
- **不做插件市场 / 在线安装 / 自动更新**——分发是独立命题（见 §13 M4）
- **不做热重载**——插件更新 = 停用 → 替换 → 启用，中间态必须是"停用"
- **不做动态库（`.so`）插件**——见 §5，这是本方案唯一的硬否决
- **不允许插件注册新的能力位或权限点**——能力位是"平台事实"的陈述，不是可扩展的命名空间
- **不允许插件直接访问面板 SQLite**——面板数据模型不是插件的 API；要给什么必须显式给
- 首版**不**让插件参与站点配置渲染、Web 终端、防火墙规则——那些是面板的安全核心路径

## 2. 现状约束盘点（为什么不能"顺手"做）

| 组件 | 现状 | 插件系统的影响 | 处置 |
|---|---|---|---|
| **依赖预算** | `ci/check-layering.sh` [8] 实测去重后第三方直接依赖约 **22 / 38**（上限 38） | WASM 运行时（wasmtime 数十个 crate）**直接超预算出局** | 方案必须是**零新依赖**；清单格式也因此从 TOML 改成 JSON（§7） |
| `cmd.rs` | 子进程**唯一出口**；`Bin` 是**固定枚举**（白名单二进制），无任意路径入口 | 插件是"任意路径的可执行文件"，现有 `run()` 表达不了 | 在 `cmd.rs` 内新增**显式路径**入口 `run_path()`——仍然只有一个 spawn 点，门禁 [1] 语义不变 |
| `CmdOpt` | 已有 `timeout` / `max_output` / `run_as`（降权）/ `working_dir` / `env` | 插件所需的超时、输出上限、降权**全部现成** | 直接复用，不新增机制 |
| `Capability{supported,backend,reason}` | 能力位必须"对实际能不能跑负责"，禁止撒谎 | 插件**不得**成为能力位的来源；否则"插件在就显示可用、插件坏了就报错" | 插件只消费既有能力，**不产生**能力位（§15） |
| `panel-os` provider traits | 强类型、按平台实现、受门禁 [3][4] 约束 | 让插件实现 trait 等于把第三方代码放进安全核心 | 插件**不进** `traits.rs`；产出走独立适配层（§15） |
| RBAC | 26 个 perm 点；自定义角色的权限必须是调用者自身权限的子集 | 插件需要独立的权限点，否则只能复用 `system.manage`（过度授予） | 新增 `plugin.view` / `plugin.manage` |
| 任务中心 | `TaskKind` 8 类，任务体是单方法 trait | 插件调用短（≤10s）且频繁，进任务中心会把列表刷满 | 插件调用**不进任务中心**；周期调用走既有 Scheduler（§13） |
| 审计 / 通知 | `audit_log` + `notifications`（含按天去重） | 安装、授权、启用、每次调用都要留痕 | 全程落审计；失败落通知 |
| 迁移 | `LATEST = 8`，逐版本可回放 | 新增 `plugins` 表 | 迁移 009 |
| 前端 | 能力矩阵驱动 UI、`CAP` 映射、菜单/路由集中定义 | 新页面必须走能力门禁，不能"能点但报错" | 新增 `PluginsView` + `plugin.manage` 能力位 |
| **systemd 硬化** | 单元**不设 `User=`**（面板确实需要 root 才能管服务/防火墙），但开了 `NoNewPrivileges` / `ProtectSystem=strict` / `ProtectHome` / `ReadWritePaths` / `MemoryMax` / `TasksMax=256` | 插件是面板的**子进程**，会继承这套沙箱——既有免费收益，也有共享配额的代价 | 见 §4.1：收益直接吃下，代价如实登记 |

## 3. 关键决策表

| # | 决策点 | 候选 | **推荐** | 理由 |
|---|---|---|---|---|
| D1 | 隔离方式 | A. 动态库载入面板进程<br>B. WASM 运行时<br>C. 子进程 + 降权 | **C** | 见 §5：A 是不可接受的（同进程同权限、崩了带崩面板）；B 在依赖预算余量有限（去重后约 22/38）时不可行 |
| D2 | 生命周期 | A. 常驻进程 + 握手/心跳<br>B. 一次性调用（one-shot） | **B** | 常驻要处理重连、僵尸、内存泄漏、孤儿回收——这些机制的成本远高于它省下的启动开销；one-shot 的超时与清理就是 `CmdOpt.timeout` + 进程回收，零新机制。常驻留到 M3 且需实测延迟证据 |
| D3 | 首版能力面 | A. 完整（含 exec / 任意写）<br>B. 只读观测 + 通知投递 | **B** | 见 §6：不给 exec 是"先别把任意代码执行引入面板"；能力面可以后加，去掉不能 |
| D4 | 完整性保障 | A. 不做任何校验<br>B. GPG 签名<br>C. 声明 + 摘要留档 + 显式安装 | **C** | **B 在没有密钥分发与信任根的前提下只是仪式**（谁签、密钥怎么发、吊销怎么做全都不存在）。C 是诚实的下限：安装是显式动作、权限清单给人看、目录摘要留档以便事后比对。**如实声明：这不是供应链防护** |
| D5 | 清单格式 | A. TOML（`config.toml` 同款）<br>B. JSON | **B** | `toml` 目前只是 `panel-cli` 的依赖；把它拉进 `panel-api` 会动依赖预算，而 `serde_json` 已经是 `panel-api` 依赖 |
| D6 | 与 provider traits 的关系 | A. 插件实现 `panel-os` 的 trait<br>B. 独立 crate + 适配层 | **B** | A 会让第三方代码进入安全核心，且破坏"能力位由平台事实决定"（§15） |
| D7 | 调用是否入任务中心 | A. 入（复用进度/取消/审计）<br>B. 不入，另设调用记录 | **B** | 插件调用是**高频短动作**（指标采集可达每分钟数次），塞进任务中心会把运维真正关心的长任务淹没。但**审计一条不漏**，调用记录另表 |

## 4. 隔离模型：为什么是"子进程 + 降权"

| 方案 | 隔离强度 | 依赖代价 | 崩溃影响 | 插件语言 | 结论 |
|---|---|---|---|---|---|
| A. 动态库（`.so`）载入面板进程 | **无**——同进程、同权限、同内存 | 零 | 插件段错误 = **面板挂**；插件可改面板内存 | 必须匹配 Rust ABI | ❌ 否决 |
| B. WASM（wasmtime / wasmer） | **强**——默认无 IO，能力必须由宿主显式注入 | 重（数十个 crate） | 无 | 须编译到 wasm，生态受限 | ❌ 本轮不可行（D1/§2 预算） |
| **C. 子进程 + 降权用户 + 超时 + 输出上限** | 中——边界是 **OS 用户权限** | 零（复用 `cmd.rs` / `CmdOpt`） | 无（面板不受影响） | 任意（shell / Python / Go…） | ✅ **采纳** |
| C+ seccomp / cgroup / netns | 强（syscall 与网络级） | 需 `libseccomp` 或手写 BPF，或依赖宿主工具 | 无 | 任意 | ⏳ M2/M3 增强 |

**必须如实说明的一点**：C 的隔离强度是"**一个低权用户能做的事**"，**不是 syscall 级沙箱**。
插件进程一旦跑起来，它读得到什么、连得上什么，只受 OS 约束——面板对此**没有技术强制力**。
因此：

1. 首版能力面刻意收窄到"不需要文件写、不需要 exec"（§6）；
2. 真正想约束网络/文件面的手段（netns、cgroup、seccomp）列 M2/M3，不写成"已经有了"；
3. 安装界面必须把这一点讲给管理员听，而不是给一个"已沙箱化"的勾。

### 4.1 宿主现成的沙箱：能吃到什么，以及它管不到什么

面板的 systemd 单元（由 `panel systemd-unit --install` 生成）**不设 `User=`**——面板确实需要
root 才能管服务与防火墙——但开了一整套硬化。插件作为面板的**子进程**会继承这套约束，
所以有几件事**不用做也得到了**：

| 硬化项 | 对插件的免费收益 |
|---|---|
| `ProtectSystem=strict` + `ReadWritePaths=<数据/日志/站点目录>` | 插件写不了这些之外的地方（`/etc`、`/usr` 全只读）——"插件写坏系统"这条路基本被堵住 |
| `ProtectHome=yes` | 读不到 `/home`、`/root` |
| `NoNewPrivileges=yes` | 插件拿不到新权限（`setuid` 提权失败）。注意它**不阻止降权**，所以 `CmdOpt.run_as` 依然可用 |
| `TasksMax=256` | 插件 fork 炸弹会撞上限而失败（面板自身也在同一配额内，见下） |
| `PrivateTmp=yes` | 插件的 `/tmp` 与**宿主及其它服务**隔离（与面板共享同一份私有 `/tmp`） |

**但它管不到的三件事，必须如实说：**

1. **内存是共享的**：`MemoryMax` 是整个面板 cgroup 的上限，**插件占用计入其中**——
   一个吃内存的插件可以把**面板本体**一起拖到 OOM。这是子进程模型最实际的代价。
   缓解手段是 M2 把插件放进独立 cgroup / scope，**首版不要假装已经解决了**。
2. **`ReadWritePaths` 对插件同样放行**：插件能写面板的数据 / 日志 / 站点目录。
   也就是说"没有 `fs.write` 权限"**不是**技术强制，只是"面板不会主动给它写的能力"。
   真正起作用的是降权用户 + 只读挂载，不是权限清单。
3. **网络没有任何约束**：`ProtectSystem` 系列不涉及网络；`net.outbound` 始终是"仅登记"。

## 5. 能力边界：**声明 ≠ 强制**

这是本设计最容易被写成"安全剧场"的地方，所以先把话说清楚。插件的权限分两类：

| 类别 | 举例 | 面板能否技术强制 | 机制 |
|---|---|---|---|
| **面板中介的能力** | `notify.push`、`data.metrics.read`、`data.logs.read:<source>`、`store.blob.write:<dir>` | ✅ **能** | 插件只能通过协议**向面板请求**；面板逐次核对已批准权限，未批准直接拒绝并审计 |
| **插件自理的能力** | 网络出站、读宿主任意文件、CPU/内存占用 | ❌ **不能** | 只受 **OS 用户权限** 约束。清单里的 `net.outbound:<host>` 是**声明 + 管理员知情**，不是强制手段 |

**所以首版能力清单（只列第一类 + 明确标注第二类为"声明"）：**

| 权限 | 类别 | 含义 | 首版 |
|---|---|---|---|
| `data.metrics.read` | 中介 | 读面板已采集的 `SystemSnapshot`（不经插件） | ✅ |
| `data.logs.read:<source>` | 中介 | 按**日志源**授权（不是"读任意文件"） | ✅ |
| `notify.push` | 中介 | 投递站内通知（级别由面板决定上限） | ✅ |
| `http.outbound:<host>` | 声明 | 插件自己发 HTTPS；面板**无法强制**，仅登记 | ✅（仅声明） |
| `fs.read:<path>` | 中介 | 面板把指定路径内容交给插件（只读、限长） | M2 |
| `net.isolate` | 中介 | 面板用 netns 让插件**连不上网**（真正可强制） | M2 |
| `cmd.exec` | 声明 | 插件自建子进程——即"降权用户的任意代码执行" | M3（独立评审） |
| `fs.write:<path>` | 声明 | 插件自行写文件 | M3 |

**`cmd.exec` 的诚实表述**：授予它等于**允许插件以该降权用户的身份执行任意代码**。
面板的 `cmd.rs` 纪律管的是**面板自己**的子进程；它管不到插件进程内部再起什么。
M3 若开放，必须同时具备：独立 OS 用户、syscall 过滤、写路径白名单、逐次管理员确认。

## 6. 插件形态与清单（`plugin.json`）

一个插件 = **一个目录**，位于 `<data_dir>/plugins/<name>/`：

```
<data_dir>/plugins/wecom-notify/
├── plugin.json          # 清单（唯一必需文件）
├── run.sh               # entry 指向的可执行文件（权限 0755，属主 = 面板所有）
└── ...                  # 插件自带资源
```

```json
{
  "api": 1,
  "name": "wecom-notify",
  "version": "0.1.0",
  "description": "企业微信机器人通知渠道",
  "entry": "run.sh",
  "timeout_secs": 10,
  "permissions": ["notify.push", "http.outbound:qyapi.weixin.qq.com"]
}
```

| 字段 | 必填 | 校验 |
|---|---|---|
| `api` | ✅ | 必须 == 面板支持的版本（当前 1）；不匹配 → 拒绝安装，**不做兼容层** |
| `name` | ✅ | `[a-z0-9][a-z0-9_-]{1,31}`，且必须 == 目录名（防"目录 A 声明成 B"的混淆） |
| `version` | ✅ | 仅记录与展示，不参与依赖解析（首版无依赖关系） |
| `entry` | ✅ | **相对路径**、不得含 `..`、不得是绝对路径；必须存在且是可执行文件 |
| `timeout_secs` | ❌ | 1~60，默认 10。面板还会对它再取 min（清单不能给自己无限时间） |
| `permissions` | ✅ | 必须在 §5 白名单内；未知权限 → **拒绝安装**（不静默忽略，也不"以后再说"） |

## 7. 协议：一次性调用的单行 JSON

面板 `spawn` 插件进程 → 写一行 JSON 到 stdin → 读一行 JSON 自 stdout → 进程退出。

**请求**（面板 → 插件 stdin，单行，末尾 `\n`）：
```json
{"api":1,"op":"notify.push","params":{"level":"warn","title":"证书 7 天内到期","body":"..."},"granted":["notify.push","http.outbound:qyapi.weixin.qq.com"]}
```

**成功响应**（插件 → 面板 stdout，单行）：
```json
{"ok":true,"result":{"delivered":true}}
```

**失败响应**：
```json
{"ok":false,"error":"webhook 返回 401"}
```

**首版 op 只有三个**：`meta`（自述，安装时调用一次，用于展示）、`collect`（产出观测项）、`notify.push`。

**协议纪律（都是"插件是不可信来源"的直接推论）**：
1. stdout **只取第一行**；后续行视为噪声丢弃；超过 `max_output` 直接截断。
2. 响应必须能被 `serde_json` 解析为**预期结构**；多余字段忽略、缺失/类型不符 → 记 `last_error` 并按失败处理。
3. `error` 文本限长（复用日志模块的截断纪律）——**插件输出不可信，不得原样拼进任何配置/命令**。
4. `collect` 产出的观测项必须过**白名单校验**：key 形如 `[a-z0-9_.]{1,64}`、value 为**有限** `f64`、单位在枚举内、条数上限 128（§15）。
5. 进程退出码非 0 且 stdout 无可解析响应 → 失败；stderr 留档供排查（同样限长）。

## 8. 数据模型（迁移 009）

```sql
CREATE TABLE plugins (
    id            INTEGER PRIMARY KEY,
    name          TEXT NOT NULL UNIQUE,
    version       TEXT NOT NULL,
    api_version   INTEGER NOT NULL,
    description   TEXT,
    entry         TEXT NOT NULL,
    enabled       INTEGER NOT NULL DEFAULT 0,   -- 安装后**默认停用**，需管理员显式启用
    perms_json    TEXT NOT NULL,                -- 已批准的权限（可以少于清单请求的）
    manifest_json TEXT NOT NULL,                -- 清单原文留档（事后审计"它当初要了什么"）
    dir_digest    TEXT NOT NULL,                -- 安装时目录内容摘要（sha2，见下）
    timeout_secs  INTEGER NOT NULL DEFAULT 10,
    installed_by  TEXT NOT NULL,                -- 首次安装者
    installed_at  INTEGER NOT NULL,
    last_call_at  INTEGER,
    last_ok       INTEGER,                      -- 最近一次调用是否成功
    last_error    TEXT
);

CREATE TABLE plugin_calls (                     -- 调用记录（不入任务中心，但审计一条不漏）
    id         INTEGER PRIMARY KEY,
    plugin_id  INTEGER NOT NULL REFERENCES plugins(id) ON DELETE CASCADE,
    ts         INTEGER NOT NULL,
    op         TEXT NOT NULL,
    ok         INTEGER NOT NULL,
    ms         INTEGER NOT NULL,
    error      TEXT
);
```

- `dir_digest` 用 **sha2**（`panel-api` 已是依赖，不动预算）：对目录内容（文件路径 + 内容）排序后求摘要。
  **它只回答"目录变没变"，不回答"变的是不是恶意"**——所以它配合 §11 的"目录变更→自动停用"使用，
  而不是被说成签名。
- `plugins` 的删除**不自动删目录**（与备份产物同哲学：删除数据要用户自己确认清楚），
  前端文案要写明这一点。

## 9. API 面（全部进 `openapi.yaml`，前端契约门禁强制）

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/v1/plugins` | GET | 列表（含 `enabled` / 已批准权限 / 最近一次调用结果） |
| `/api/v1/plugins` | POST | **安装**：`{name}` → 校验 `<data_dir>/plugins-inbox/<name>/plugin.json`、展示权限清单、原子搬入并注册 |
| `/api/v1/plugins/{id}` | PATCH | 启停 / 改超时 / **调整已批准权限**（只能减不能加，加权限必须重新安装并确认） |
| `/api/v1/plugins/{id}` | DELETE | 删除注册（`confirm` 词 = 插件名；**不删目录**，文案写明） |
| `/api/v1/plugins/{id}/invoke` | POST | 手动调用（`op` + `params`），用于排障；受 `plugin.manage` + 审计 |
| `/api/v1/plugins/{id}/calls` | GET | 最近调用记录（默认 50 条） |

- **权限**：`plugin.view`（读列表/记录）、`plugin.manage`（安装/启停/删除/调用）。
- **能力位**：新增 `plugin.manage = yes("builtin")`（面板内建，不依赖外部二进制），
  与 `backup.manage` 同款。**注意：现有 `Tier` 只决定采样间隔 / 任务并发 / 保留条数
  （见 `panel-core` 的 `Tier`），并不参与能力位判定**——将来若要"低配档关闭插件系统"，
  需要**新增**这个机制，而不是假定它已经存在。
- 安装**不接受 URL / 上传**：管理员自行把插件目录放到 `plugins-inbox/`，面板只做校验与注册。
  少一条上传通道 = 少一个攻击面；在线分发留 M4。

## 10. 前端（对齐现有交互语言）

- 新页 `PluginsView`：插件列表（名称/版本/状态/权限徽章/最近调用）+ 「安装」面板
  （填目录名 → 预览清单与权限清单 → 逐项确认）+ 权限调整 + 调用记录。
- **权限清单必须逐条展示并解释含义**，尤其是 `cmd.exec` / `fs.write` 这类"声明型"权限——
  要写明"面板无法强制，仅登记"。给一个笼统的"信任此插件"勾选框等于把责任推给用户。
- 插件上报的观测项在概览/专业监控页以**独立分组**展示，**不混入**面板自采数据：
  用户必须能一眼看出哪些数字来自第三方代码。
- 插件停用时相关 UI 一律置灰并给出原因（能力驱动 UI 的既有纪律）。

## 11. 安全护栏

1. **安装即显式**：安装 → 展示权限清单 → 管理员确认 → 注册但**默认停用** → 再显式启用。三步都不省。
2. **降权执行**：插件进程经 `CmdOpt.run_as` 以**专用低权用户**运行（默认 `nobody` 或面板配置的账号），
   **绝不以面板进程身份运行**——面板进程是 root（改配置、reload nginx、读写系统目录），
   以它运行插件等于把宿主机的完整控制权交出去。
3. **目录变更 → 自动停用**：每次启用前重算 `dir_digest`，与登记值不符则**拒绝启用**并告警。
   这挡住"装完之后再往里塞代码"的路径（它不是签名，但能挡住这种最常见的绕过）。
4. **输出即不可信**：严格遵守 §7 的协议纪律 1~5；插件输出与"用户在浏览器里填的字符串"同级对待。
5. **调用限流**：单插件并发调用上限 1（one-shot 模型下天然成立），每分钟调用次数上限可配，
   防止插件把面板变成进程fork 放大器的间接工具（周期调用走 Scheduler，天然受调度器约束）。
6. **只减不增**：PATCH 只能缩减已批准权限。要加权限必须重新走安装流程——授权扩大必须重新确认。
7. **审计**：安装 / 授权 / 启停 / 每次调用（op + 结果 + 耗时）全部落 `audit_log`；
   调用失败落通知（按天去重，复用通知模块的既有纪律）。

## 12. 分期落地（每期独立验收，未启用时基线行为不变）

| 期 | 范围 | 验收 | 风险 |
|---|---|---|---|
| M1 只读 + 通知 | `cmd.rs::run_path` + 注册表/迁移 + 安装/启停 + `meta`/`collect`/`notify.push` + `PluginsView` | 放一个目录 → 安装 → 看到权限清单 → 启用 → 概览出现第三方观测分组 | 🟡 中（引入外码执行路径，但能力面不含写） |
| M2 受控读与网络隔离 | `data.logs.read:<source>` / `fs.read:<path>` + `net.isolate`（netns）+ 调用限流 | 插件只能读到授权日志源；声明 `net.isolate` 时确实连不上网 | 🟡 中（netns 依赖宿主能力，需如实降级） |
| M3 受控写（另立项） | `cmd.exec` / `fs.write:<path>` + seccomp/cgroup + 逐次确认 | — | 🔴 高（等于开放降权用户任意代码执行，须独立评审） |
| M4 分发（另立项） | 签名与信任根、在线安装、插件市场 | — | — |

**回滚保证**：全部改动在 `plugins` 命名空间内（新表、新 crate、新路由族、新页面）；
不上传/不安装任何插件时，`AppState` 既有字段与代码路径零介入，单机行为与今天一致。

## 14. 与既有强类型边界的关系（本方案最关键的一节）

面板的现有强度来自"**每一条能力都由强类型 trait + 能力位 + 门禁三件套支撑**"。
插件系统若处理不好，会从侧面把这套东西掏空。三条硬边界：

1. **插件不实现 `panel-os` 的 trait。**
   `SiteSpec` / `SystemSnapshot` / `FileProvider` 这些类型的构造点是安全核心——
   插件一旦能构造它们，门禁 [3][4] 与"能力位不撒谎"就同时失效。
   插件产出走**独立适配层**：`plugin → serde_json::Value → 校验 → 面板内部类型`。
2. **插件不产生能力位，只消费已授权的既有能力。**
   反例（必须避免）：插件往能力矩阵里塞一个 `gpu.metrics` 位，插件坏了界面还显示可用。
   正确形态：插件上报的观测项是**数据**，不是**能力**；界面上它们属于"第三方数据"分组。
3. **插件产出以"不可信输入"对待。**
   与浏览器传入的字符串同级：限长、限类型、白名单枚举、绝不直接拼进 nginx 配置 / SQL / argv。
   这条不是洁癖——`sites.rs` 里"值会进 nginx 配置文本，所以必须单 token"的判断，对插件输出同样成立，
   而且插件的来源比浏览器更不可控。

**一句话概括**：插件是**被面板调用的外部程序**，不是**面板的一部分**。它得到的每一份数据、
能做的每一件事，都必须是面板**显式给**的，不能是它**自己够**到的。

## 15. 风险登记

| 级别 | 风险 | 缓解 |
|---|---|---|
| 🔴 | `cmd.exec` 一旦开放 = 降权用户的任意代码执行 | M3 才评审；首版能力面不含它；开放时须同时具备独立用户 + syscall 过滤 + 路径白名单 + 逐次确认 |
| 🔴 | **声明型权限无法技术强制**（网络/文件） | 界面如实说明"仅登记"；`net.isolate`（M2）提供真正可强制的断网；降权用户是第一道也是当前唯一一道边界 |
| 🔴 | 依赖预算约 22/38（上限 38），余量有限；wasmtime 等数十 crate 的重方案仍直接超预算出局 | 本方案**零新依赖**（复用 `cmd.rs` / `serde_json` / `sha2`）；清单用 JSON 而非 TOML 正是为此 |
| 🟡 | 无签名 → 供应链风险 | 如实声明"不是供应链防护"；`dir_digest` + "变更即停用"挡住最常见的"装完再塞代码"；签名列 M4 |
| 🟡 | 插件输出畸形/超长/malicious JSON | §7 协议纪律 1~5：单行、限长、严格结构、白名单 key、有限 f64 |
| 🟡 | one-shot 启动开销（Python 插件约数十毫秒） | 周期采集的间隔天然 ≥ 30s；若实测成为瓶颈，M3 再评估常驻模型（需先有延迟证据） |
| 🟡 | 插件进程成为 fork 放大器 | 并发上限 1 + 每分钟调用上限 + 周期调用走调度器（`TasksMax=256` 是最后一道兜底） |
| 🟡 | **插件内存计入面板 cgroup**（`MemoryMax`）→ 可把面板本体一起拖到 OOM | M2 用独立 cgroup / scope 隔离；**首版如实登记为已知代价**，不宣称已解决 |
| 🟡 | `ReadWritePaths` 对插件同样放行 → 插件能写数据 / 日志 / 站点目录 | 不把"无 `fs.write` 权限"当作强制手段；靠降权用户 + 只读挂载；M3 再引入写路径白名单 |
| 🟢 | 与单机基线行为回归冲突 | §12 回滚保证：独立命名空间，未安装插件时零介入 |

## 16. 待决问题（落地前需要拍板）

1. **专用低权用户的落点**：用系统已有的 `nobody`，还是安装时创建一个 `panel-plugin` 用户并
   给插件目录设 ACL？前者零运维但所有插件共享身份（互相可见），后者更干净但引入用户管理动作。
2. **`collect` 产出的观测项是否需要持久化**：不落盘（与 SSE 同哲学，省盘）还是落时序表
   （可看历史，但低配盘压力大）。倾向：**默认不落盘，只做当前值展示**，历史留给 M3。
3. **权限清单的粒度**：`data.logs.read:<source>` 的 source 用什么标识——
   复用日志模块的 source id（需要它稳定）还是允许路径前缀。
4. **是否允许插件声明"需要 GUI 配置项"**（让面板渲染它的配置表单）。首版倾向**不允许**：
   插件配置一律走环境变量/自身文件，面板不代渲染表单——否则插件就获得了往面板 UI 注入内容的能力。
